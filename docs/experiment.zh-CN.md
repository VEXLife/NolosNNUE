# 初始自举实验记录

[English](experiment.md) | 简体中文
## 问题

是否能用自写 HCE 搜索与自对弈，在没有外部数据或参数的情况下训练 NNUE，并逐代提升？本项目已经实现可运行的流程；这次小实验尚未证实棋力提升，也不能据此认定扩大规模就一定成功。

## 实际执行

2026-10-02，在本地 CPU 上运行最终修正版（禁止探索跳过强制防守，并固定跨代验证分组）。自对弈与竞技评测为 15 路自由五子棋，搜索限深 3、每步最多 1500 节点、非根节点分支上限 12、冲四静态搜索预算 6 层。不是 GPU 实验。训练使用当时的 CPU 稀疏 batch 实现；后续 GPU 批处理改动尚未在 NVIDIA 硬件上做性能实测。

```bash
cargo build --release --bins
./target/release/selfplay --games 512 --nodes 1500 --depth 3 \
  --threads 4 --output artifacts/hce-selfplay.jsonl
uv run --frozen --extra cpu -m trainer.train --data artifacts/hce-selfplay.jsonl \
  --output artifacts/generation-0.nnue --epochs 60 --threads 2 --seed 42
./target/release/arena --candidate artifacts/generation-0.nnue --baseline hce \
  --pairs 128 --nodes 1500 --depth 3 --threads 4 \
  --output artifacts/generation-0.arena.json
```

上面的命令使用当前 CPU dependency extra；保留的结果来自 GPU 批处理更新之前。自对弈默认种子 1，探索率 0.1，默认 HCE 教师。生成 512 局、8597 个非终局训练局面，无截断局。501 局产生可用于训练的非必胜分值，其余对局只有被过滤的战术位置。按整局分组：7196 个训练位置，1401 个验证位置；验证集含 75 局。

## 后续实验由用户运行

首轮只有约 8 千个局面，而 Rapfi 论文实验使用约 3080 万个来自强教师的局面。数据数量、搜索标签质量、网络结构和分支筛选都可能影响结果；不能把“需要更多数据”当作已经验证的唯一原因。

建议先用 README 的较小流程验证本机，再运行大规模自举命令。需要关注：

- 竞技得分而非仅训练损失；始终保留固定 HCE 对照。
- 每代都对上一代和 HCE 做执黑／执白交换的成对比赛。
- 加深教师搜索、增加探索与开局覆盖，再增加局数；避免只反复学习少量类似局面。
- 至少观察多个种子，保留失败代；若长期无法晋升，应检查特征表达和候选剪枝，而不是无限放大计算量。

原始 `.jsonl` 和 `.pt` 留在本地，不提交体积较大的训练数据或恢复检查点。生成器按每局种子确定开局与探索，在无时间截断的固定节点预算下结果可重建；多线程文件行顺序可能不同，文件级 SHA-256 因而可能不同。训练器对输入排序，使对局分组和样本顺序可重复。后续训练内核或硬件改变仍可能使浮点优化结果与历史检查点不同。

## 已完成的验证

- Rust 单元／集成测试：棋形增量更新、哈希与撤子、全部八种棋盘对称性、胜负规则、真假三、双四及成五优先、强制着法、协议事务和中断。
- 真实原生进程：CRLF、静默同步、搜索中断、单次回复、禁手及终止。
- 真实 WASM：共享协议、ABI、网络加载、损坏文件拒绝与搜索中断。
- PyTorch、原生 Rust、WASM 数值一致性：100 个生成局面，允许不超过 1 分的浮点差异。
- 浏览器：黑白人机、分析不落子、停止、悔棋、本地／URL 权重、坏权重保留原网络、禁手与棋谱导入导出、手机布局。
